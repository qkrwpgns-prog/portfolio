## 한눈에 보기

- **문제**: 거래 문의 채팅의 첫 응답까지 평균 6시간이 걸려 거래가 자주 무산됨
- **내가 한 일**: 실시간 알림 서버 설계·구현, 팀 일정 관리
- **결과**: 첫 응답 시간 6시간 → 40분, 거래 성사율 31% → 52%

## 배경과 문제

학과 커뮤니티의 중고거래 게시판은 댓글로만 연락할 수 있어 판매자가 문의를 늦게 확인했다. 설문(응답 87명)에서 "답이 늦어서 다른 데서 샀다"는 답변이 가장 많았다.

## 내 역할

4명 중 백엔드를 혼자 맡았다. 채팅·알림 서버와 DB 설계, 배포를 담당했고 팀장으로 주간 회의와 일정을 관리했다.

## 해결 과정

### 핵심 결정 — 폴링 대신 WebSocket + 푸시 알림

처음에는 10초 간격 폴링으로 구현했지만, 사용자가 앱을 닫으면 알림이 가지 않는 문제가 남았다. WebSocket으로 앱 사용 중 실시간 전달을 하고, 접속하지 않은 사용자에게는 FCM 푸시를 보내도록 나눴다.

### 트러블슈팅 — 서버 2대에서 메시지가 사라지는 문제

서버를 2대로 늘리자 메시지 일부가 상대에게 도착하지 않았다. 두 사용자가 서로 다른 서버에 연결되어 있으면 메시지가 전달될 길이 없었기 때문이다. Redis Pub/Sub으로 서버 간 메시지를 중계하도록 바꾸고, 부하 테스트(동시 접속 300명)에서 유실 0건을 확인했다.

## 결과

| 지표 | 전 | 후 |
|---|---|---|
| 첫 응답까지 평균 시간 | 6시간 | 40분 |
| 거래 성사율 | 31% | 52% |

## 배운 점과 다음에 다르게 할 것

- 기술 선택 전에 **"사용자가 앱을 안 켜고 있을 때"** 같은 경계 상황부터 적어 봐야 한다.
- 수평 확장은 처음부터 고려하지 않으면 구조를 다시 짜게 된다. 다음엔 상태를 서버 메모리에 두지 않는 것부터 시작하겠다.
